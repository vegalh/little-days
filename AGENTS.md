# AGENTS.md

Rules for any coding agent working in this repository.

## Read first

1. `PRD.md` — what to build. It is the source of truth for features and behavior.
2. `DESIGN.md` — how it should look. Follow it before styling anything.
3. `PROPOSAL.md` — the original idea, for background only.

If these files disagree, PRD.md wins for behavior and DESIGN.md wins for appearance. If something isn't covered, ask instead of guessing.

## The main rule

**Use the simplest code that works, and add nothing I did not ask for.**

That means:

- Build only what PRD.md describes. No extra features, settings, pages, or "nice to have" additions.
- No frameworks, libraries, build tools, bundlers, or TypeScript. No React, no Vite, no Tailwind. The site runs by opening the page from a static server.
- The one exception is testing: `package.json` exists only to install Playwright as a dev dependency. It has no runtime dependencies, and the site never loads anything from `node_modules`.
- Nothing loaded from a CDN or any outside URL: no hosted web fonts, no icon sets, no stylesheets, no other scripts. The only fonts are RootMap's Caveat and Nunito, bundled as files in `assets/fonts/` (SIL Open Font License); don't add others. The only outside things the page uses are:
  - Google's Maps JavaScript API script, for the results map only (it then loads its own code and makes its own requests to Google)
  - Open-Meteo Forecast and Nager.Date, called with `fetch`
  - plain links to Google Maps (`https://www.google.com/maps/search/?api=1&...` and `https://www.google.com/maps/dir/?api=1&...`) that the adult can follow
- Plain HTML, CSS, and JavaScript.
- Prefer a short, readable function over a clever one. Prefer fewer files over more.
- Don't add abstractions, config systems, classes, or helpers until the same code is needed in at least two places.
- Don't add comments that only repeat what the code says. A short comment explaining *why* is fine.
- Don't refactor or reformat code you weren't asked to change.

Everything in data/ and js/ except app.js and google.js has no page code, so tests can run it in Node. Keep it that way: logic and thresholds go there, DOM code goes in js/app.js or js/google.js. Everything that touches `google.maps` stays in google.js.

Don't add files or folders beyond these without asking. Add each file only in the phase that needs it (PRD.md section 11).

## APIs and keys

| API | How it's called | Key |
|---|---|---|
| Maps JavaScript API | Google's bootstrap loader, then `google.maps.importLibrary("maps" / "marker")`, for the results map only | Browser key from `config.js` |
| Maps JavaScript API, Street View | `importLibrary("streetView")` in place details, only when "Show Street View" is pressed | Same browser key |
| Open-Meteo Forecast | `fetch` | None |
| Nager.Date | `fetch` | None |
| OpenStreetMap (Overpass) | Only by `tools/import-osm.py`, run by hand to regenerate places.js. The page never calls it | None |

Places API and Routes API are not used: they're what made the site cost money. Places come from places.js, and walking times are Little Days estimates from distance (explore.js).

**Google rules**

- Never call Google's REST web services with `fetch`, and don't add the `places` or `routes` libraries back without asking. The map is the only Google part.
- The browser key is read from `window.LITTLE_DAYS_CONFIG` in `config.js`. Never write a key into `index.html`, `app.js`, any other committed file, a test, or a commit message. Never commit `config.js` or a `.env` file. If you see a real key anywhere tracked by git, stop and tell me.
- A browser key is visible to anyone who opens the page. What protects it is the website restriction and the API restriction (Maps JavaScript API only) in Google Cloud, so never suggest removing them.
- Never copy Google names, addresses, photos or walking times into places.js or any other file: Google's terms don't allow storing them. places.js holds only OpenStreetMap data and the school's own photos.
- Keep Google's logo and attributions visible on the map. Where places are listed, show "© OpenStreetMap contributors" (ODbL). Never hide or cover either.
- One results map per visit, created only when Explore shows results; markers are reused.
- Place details offer "Show Street View": one `StreetViewPanorama` from the Maps JavaScript API (no other API to enable), reused for every place and shown only when pressed, since each view is billed past 5,000 a month. The lookup (`StreetViewService.getPanorama`) is free.
- Card photos are never Google's: only the school's own or openly licensed ones from Wikimedia Commons, saved in images/places/ with their credit shown on the card.
- Don't add a backend, a serverless function or a second key. If a feature seems to need one, stop and ask.

**fetch rules** (Open-Meteo Forecast, Nager.Date)

- Use `fetch()` with `await` inside an `async` function. No `.then()` chains, no XMLHttpRequest.
- Wrap it in `try/catch`.
- Check `response.ok` before reading the body, because a 404 or 400 does not throw.
- Send Open-Meteo latitude and longitude rounded to 2 decimals.
- Use only the field names listed in PRD.md 7.2. Don't guess field names. If you need a field that isn't listed, `console.log` the real response first and tell me what you found.

**The map** follows the same idea: `await` inside `try/catch`, and handle `window.gm_authFailure` for key problems. Without the map, the places, links and weather still work.

On any failure, show the matching state from PRD.md section 8 and `console.error` the details. Never fill a failed or missing value with a guess, a fixture or old data.

Keep the API code short and easy to follow. I have to be able to explain every line of it myself.

## Data and storage

- Activities live in `activities.js`, in the shape PRD.md 7.5 describes.
- Every activity comes from RootMap. Don't write new activities or change anything inside an entry's `rootmap` part: it is the original text, copied from RootMap at the commit named at the top of the file. Little Days additions go only in `littleDays`.
- Never present a Little Days judgement (category, access, indoor/outdoor, weather note, age note, guide, place, weather, season, holiday tag) as if it came from Google or RootMap. Label it as PRD.md 7.16 says. Holiday tags are shown as "holiday-inspired".
- Exploration guides in `guides.js` are about a kind of place, never a specific one. Never write that a place has, offers or allows anything. Draft them for my review; don't treat a draft as final.
- Never change the RootMapMVP repository.
- To refresh activities or photos from RootMap, run `python3 tools/import-rootmap.py` (needs Node and Pillow). It keeps the hand-reviewed `littleDays` fields (place, weather, seasons, holidays) from the current activities.js and records the RootMap commit in the file header. Don't hand-edit `rootmap` parts or the generated photos.
- Public holidays come only from Nager.Date. Other celebrations go in `celebrations.js` with the countries where they're widely observed. Don't show a celebration everywhere, and word its ideas as optional ("If your family celebrates…").
- Use only the `localStorage` keys in PRD.md 7.18. Store place IDs, activity IDs, ISO dates, fixed choices and the adult's own notes. Never store children's details, device coordinates, the example address, or Google content.
- When a stored shape changes, add a versioned key and a migration that keeps the old data (PRD.md 7.9, 7.18). Never drop saved data without one.
- No cookies, no backend, no database, no analytics.
- Wrap `localStorage` reads and writes in `try/catch` so the page still works if storage is blocked.

## Safety and honesty on the page

- The page must never say outdoor play, a place, a walk or a route is "safe". Weather advice stays conservative (PRD.md 7.4, 7.15).
- A Google walking route is not proof a route suits young children or a group. Always show the route reminder (PRD.md 7.12).
- Never invent places, walking times, weather, opening hours, prices, access rules or programs. Missing data is shown as missing.
- Never say a business accepts children or classroom visits.
- Never ask for the device's location: every walk starts at the school (places.js).
- Never send the age range, mode, notes or anything about a child to any API.

## States

Every state in PRD.md section 8 (empty, loading, error, invalid input, in use) must look and behave exactly as written there, with the wording given. Build each error state together with the call it belongs to, and test it in DevTools (Network → Offline, blocking a domain, Sensors → Location).

## HTML

Use semantic HTML: `<header>`, `<main>`, `<section>` with headings, `<form>` for the search, `<label>` for every input, `<fieldset>` and `<legend>` for radio groups and checkboxes, `<button>` for every action, `<dialog>` for activity and place details. No clickable `<div>`s. It must be readable on a phone.

## Testing

- After any change to a logic file, `guides.js` or `activities.js`, run `node --test`.
- After any change to the page, run `npx playwright test` (desktop and phone projects).
- Playwright tests mock every outside request (PRD.md 10.2). Never let a test call a real API, and never put a real key in a test.
- Mocked tests show the page handles responses. They don't show the real APIs work. Only a passing run of `docs/LIVE-CHECK.md` does, and only I can supply the key for it.
- When reporting, say which results come from mocked tests and which from a live check. Never call a feature live-verified based on mocks.
- After a change, also open the page on a local static server and check it by hand, including at phone width. Say what you checked.

## Working style

- Work one phase at a time (PRD.md section 11), and within a phase one piece at a time, as I ask for it. Don't build the whole app in one go.
- At the end of each phase: say what changed, run the tests, report failures and limitations, and name the next step. Then stop and wait for me.
- If a step needs a Google key I haven't provided, build it with mocked tests, then tell me exactly what to set up to check it live.
- Commit and push finished work directly to `main` (no branches unless I ask), in small commits, each with a clear message saying what changed. A push to `main` deploys the site, so run the tests first. Don't open a pull request or merge unless I ask.
- If something is broken or you skipped a step, say so plainly.
