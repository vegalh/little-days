Recommendation: B, the Field Guide

B suits a teacher best, and it's the only one that works within today's cost and search rules.

A teacher's real question is "what is worth a walk with this group?", not "what is at this coordinate?". B answers that on the first screen, before any address is entered, using content you already own. Its result entries also have room for the things a teacher weighs: the walk, the round trip, the idea and the access note.

Two things worth borrowing from the others: A's link between pins and places, already in B, and C's restraint in the number of controls. B has a real cost too: results are a longer scroll than A or C, so the map scrolls away on phones.

Tradeoffs

A · Map First

Strengths

  • Strongest sense of place, and distance is obvious at a glance
  • Pin and card stay in sync, so comparing nearby options is quick
  • Familiar to anyone who uses a maps app

Weaknesses

  • Looks empty until there's a location, and says the least about why you're here
  • Reads as a utility, which is the "map app" feeling DESIGN.md warns against
  • Ideas get two lines, and reading the full list takes an extra gesture

Rule changes needed

  • A map before any search: one billed map load per visit (PRD 7.16, 9.3)
  • Drops DESIGN.md's "no floating search bar over the map"
  • The full list covers the map, but PRD 7.16 says the two are always shown together

B · Field Guide

Strengths

  • Purpose is clear in seconds, even before searching
  • Warmest and most distinctive, and clearly not a dashboard
  • Room for ideas and classroom notes without feeling cramped
  • Settings become one readable sentence

Weaknesses

  • Longest page, and the map scrolls away on phones
  • Photos show activities, not the places, and that needs a clear label
  • Photo quality sets the tone, so a weak photo hurts more here

Rule changes needed

  • None for cost or search. It keeps the "Explore nearby" press and creates no map early.
  • DESIGN.md needs updating: warm paper background, category photos

C · Minimal

Strengths

  • Lowest effort: the fewest steps from opening to results
  • Walking time reads fastest, thanks to the right-aligned column
  • Easiest of the three to build and maintain

Weaknesses

  • Least personality: the first screen could belong to any app
  • Gives no reason to explore before you commit to an address
  • A mistaken address runs a full paid search straight away

Rule changes needed

  • Drops the rule that only the button starts a search (AGENTS.md, PRD 7.1). With All as the default, each address picked costs up to 6 nearby searches.

The search bar: what went wrong and how it's fixed

Cause. The committed CSS styled the wrong layer. Google's element draws its own box on the host: :host { border: 1px solid black; border-radius: 3px }. Our CSS left that alone and drew a second, rounded box on ::part(input). That gives the rectangle with a rounded input inside it.

What's left. Your uncommitted working copy already moved the border to the host, which fixes the resting state. The focused state still shows two edges, because Google's focus ring sits inside our pale 1px border.

Which layers are whose.

  • Google's: the outer box defaults, the search icon in a 48px slot, the input, the focus ring, the clear button, the suggestion list and its attribution, and the phone dialog.
  • Ours: anything we set on the element and on its documented parts. There should be exactly one edge, and it belongs on the element.

The fix. It uses only what Google documents: the element's own CSS properties and its input and focus-ring parts. The element gets no border, a shadow draws the resting edge, and on focus that edge gives way to Google's ring, so only one line ever shows.

gmp-place-autocomplete {
  display: block; width: 100%; height: 52px;
  color-scheme: light;
  font-family: var(--font-body); font-size: 16px;
  color: var(--ink); background-color: #fff;
  border: 0; border-radius: 16px;
  box-shadow: 0 0 0 1px var(--line), 0 6px 18px rgba(38,37,31,.08);
}
gmp-place-autocomplete:focus-within { box-shadow: 0 6px 18px rgba(38,37,31,.08); }
gmp-place-autocomplete::part(input) { background: transparent !important; border: 0 !important; text-overflow: ellipsis; }
gmp-place-autocomplete::part(focus-ring) { border-color: var(--accent) !important; }

Limits of Google's widget.

  • Phones: at 450px and under, the first typed character opens Google's own full-screen dialog, with suggestions directly under the input and so above the keyboard. We keep it as it is. It can't take our styling, and any layout must expect it.
  • Location button: the widget has no documented place for one, so it sits beside the field or on the map, never inside.
  • Height: 52px isn't a documented setting. It worked in testing, but it could change with a Google update.
  • Chinese suggestions: suggestion rows use Google's fonts unless we style them further.

Tested so far: the real element at 360, 390 and 430 wide, in English and Chinese, at rest, focused and with long addresses, plus the phone dialog with an empty reply. Places requests were blocked or answered locally, so nothing billable ran.

Not tested yet: real suggestions, and real iPhone and Android keyboards. Those need a short live check before final sign-off.

What the research changed

  • Google Maps: search is a single object, and content sits in a sheet that slides over the map. That shaped A.
  • Airbnb: one search capsule, then categories, then real content straight away. Filters are never the first thing you see. That shaped B's first screen.
  • Google's Autocomplete reference: style the element and its documented parts, and leave the internals alone.
  • Nielsen Norman Group: two levels at most, with a clearly labeled way to the second. All three concepts use one Filters sheet, and nothing sits deeper than that.

Also found while inspecting

  • One failed suggestion request drops the whole address field. gmp-error triggers the weather-only fallback, so a brief network blip while typing replaces the search with the city box.
  • White on --accent is 3.79:1, below the 4.5:1 AA level, and that's the "Explore nearby" button. The prototypes use the existing --leaf-ink (6.10:1) instead.
  • The phone bottom bar stops 24px short of the right edge at 390px wide (366px of 390px).
  • refreshPartStyles() may no longer be needed. Removing it made no visible difference in headless Chromium, though that's one browser, so check it live.
